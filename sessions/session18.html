16.3 Case session 18: “From prediction to validation: How do we know our model works?”

At NeuroPhaRma Inc., a biotech company developing tools for early detection of Alzheimer’s disease, the research team has developed a prediction model to predict individual patient’s cognitive impairment using their age, sex, cerebrospinal fluid biomarkers, and APOE genotype.

The model performs well on the data used to develop it. The team is excited: could this tool help clinicians identify patients who need further assessment?

Before the company presents the model to potential clinical partners, however, the biostatistics team must answer a crucial question:

“The model makes predictions. But how well can we trust them in real patients?”

As a junior biostatistician, you have been asked to evaluate the model before it moves forward. You must assess how well it distinguishes patients with and without cognitive impairment, whether its predicted probabilities reflect the risks actually observed, and whether its performance holds up in new data.

Your task is to evaluate whether the model’s predictions can be trusted.

  1. How would you assess whether the predicted risks agree with the observed frequency of cognitive impairment, and whether the model systematically over- or underestimates risk?
  2. How would you determine how well the model distinguishes between patients with and without impairment?
  3. Finally, how would you investigate whether these properties hold in new patients, rather than only in the data used to develop the model?

At the project meeting, you will need to advise the team: is the model reliable enough to be considered for use in clinical practice, and what further evidence is needed before it can be trusted?

16.4 Discussion task: To cause or to predict

https://www.psykiatri-regionh.dk/presse-og-nyt/nyheder-og-pressemeddelelser/sider/f%C3%A6rre-akutte-genindl%C3%A6ggelser-i-psykiatrien-med-hj%C3%A6lp-fra-kunstig-intelligens.aspx?utm

While causal models are great for knowing how effective a thing is, sometimes you just want to know how likely this is to happen.

For example, suppose you’re into gambling and want to bet money on horse rides at Aalborg Travbane. You don’t need info on why a particylar jokey and horse wins — you’ll be happy just knowing whether it wins or not. The great thing about prediction models is that it will take any horse and provide a prediction. Thus, prediction models are capable of making individual judgements.

But consider the counter example. You are told that your dog is sick and will likely die. This information is worthless without knowing what to do about it. You want an intervention — a trick to counteract the sickness. This requires causal information. Often, the veterinarian will not know exactly what your dog needs, but they will know that any dog will get sick from eating chocolate. Indeed, some unique dogs might tolerate it better, but the negative effect is causal on a population level.

Most scientific fields bennefit from both approaches. Take the weather, for example. The majority of people don’t care why it will rain or why the temperature drops 10 degrees over night. But it is expremely useful information to the industry (formers, sailors, outdoor events, public transportation). And most people want to know the weather in their specific part of the world. But in the face of climate change, we also need to know why the earth is experiencing global warming. Just knowing that the earth will be 1.2 degrees warmer in 10 years will not help us keep the temperature lower or prevent the disaster.

Read about this PhD-project at AAU: https://www.cs.aau.dk/kunstig-intelligens-kan-forudsige-hvor-laenge-du-skal-vaere-indlagt-n89354?utm

Discuss:

  1. How are variable selection and confounding treated in prediction models?
  2. What decision does the prediction help with?
  3. Could a variable be very useful for predicting length of stay without causing a longer stay?
  4. Would you trust the model if it made very accurate predictions but you didn’t understand why it worked?
  5. What would be different if the hospital wanted to know what intervention would shorten the patient’s stay?

Prediction models cannot inform intervention. Only risk assessment and potential willingness to act — but what to act on?

16.5 Our dataset context

The ad_validation_logistic data are particularly convenient because they already contain observed classes and out-of-sample predicted probabilities from a logistic regression model.

The dataset was made based on the following logistic regression classifier:

# Logistic regression
model <- glm(
  impairment ~ age + male + tau + p_tau + Ab_42 + Genotype,
  data = train,

)

So

\[ \text{impairment}_i \sim age + male + tau + p\_tau + Ab\_42 + genotype \] where:

  • age: Normalized unit
  • male: Reported sex was male

16.6 The ABCD Workflow

You have read the paper by Steyerberg & Vergouwe, 2014 (1) in which they propose an ABCD framework for validating prediction models. The acronym is:

  • A = calibration-in-the-large,
  • B = calibration slope,
  • C = discrimination/C-statistic,

16.7 Preparing the data

A prediction model can be evaluated from two things:

  • what actually happened;
  • and what the model predicted.

Here we use predictions from a logistic regression model. The model has already been trained, so we do not fit a model. We focus on evaluating its predictions.

ad_validation_logistic <- medisr::ad_validation_logistic

As we can se, the prediction model is actually not making binary (yes, no) predictions. This is crusial knowledge! Most prediction models make probability statements, saying that:

\[ p(\text{impaired} | θ_i) = x_i \]

In words:

The model probability for being impaired is given by all subject-specific predictors, θ. Thus, it logically follows that the probability for not being inpaired is \(1 - p(\text{impaired} | θ_i)\).

However, we need to draw a line in the sand somewhere, in order to evaluate the model.

To work with our data, we must turn probabilities into classes. Here we use 0.5 as the threshold: if the predicted probability of impairment is at least 0.5, we classify the participant as impaired; otherwise, we classify them as a control.

In R, this is as easy as this:

predictions <- ad_validation_logistic |>
    mutate(
        .pred_class = probably::make_two_class_pred(
            .pred_impaired,
            levels(Class),
            threshold = 0.5 )
        )

In a clinical reality, however, this is a complex issue that needs careful and clever decisions. We have therefore dedicated a full session (later) for tackling this specific decision. For the remainder of this session, we’ll not discuss the clinical implications of the threshold.

16.8 Quantifying binary prediction success

In binary outcomes, there’s really only four cases:

  1. The model predicted class A, which was correct
  2. The model predicted class A, which was incorrect (it was B)
  3. The model predicted class B, which was correct
  4. The model predicted class B, which was incorrect (it was A)

We need to work with these four cases in a clever way.

As you will see from this session, the field has defined countless of interesting and sophisticated ways to work with this type of data.

We’ll start by organizing the raw data in a matrix. This matrix is the foundation for almost all outcomes we’ll work with, such as accuracy, specificity, sensitivity.

This will also lead to the idea of the receiver operating characteristic (ROC) and area under its curve (AUC).

16.8.1 It all starts with the confusion matrix

As always, we’ll start simple and build up the complexity.

Imagine a model which predicts cognitive impairment solely by the level of CSF amyloid beta plaque concentration. The model receives a concentration value and feeds back a probability. We can visualize this imaginary model as Figure 16.2.

How many was correctly classified?

We can make a confusion matrix — a 2×2 table that shows how many observations were classified (in)correctly for each class.

For the fictitious data we plotted in Figure 16.2, the confusion matrix would be:

True: impaired True: control
Predicted: impaired 4 1
Predicted: control 0 4

yardstick has a function to compute this for our larger dataset. Recall that we have multiple predictors, so this would have been impossible to plot in a 2D coordinate system 😅

conf_mat(
  predictions,
  truth = Class,
  estimate = .pred_class
)
          Truth
Prediction impaired control
  impaired       25      14
  control        19     109

A confusion matrix is useful because it lets us see what kinds of mistakes the model is making, rather than giving us just one summary number.

We spot an interesting pattern:

  • There are many more control participants than cognitively impaired participants.
  • labeling the cognitive impairment was not a success — only 25 out of 44 were labeled correctly!
  • labeling the control participants much better — 109 out of 123 were labeled correctly!

Imbalanced data can cause several issues. In our dataset, there are many more controls than cognitively impaired participants. The model can therefore appear to perform well simply by being good at predicting the more common class.

So rather than looking only at the percentage of observations classified correctly, we can use metrics that explicitly describe different types of classification errors.

We can quickly calculate four relevant metrics by hand:

Prediction  Truth Impaired (Positive) Control (Negative)
Impaired (Positive) TP = 25 FP = 14

Metric Formula Result
Sensitivity (TPR) TP / (TP + FN) 56.8%

False Positive Rate FP / (FP + TN) 11.4%

False Negative Rate TP + TN / (TP + TN + FP FN) 80.2%

where:

  • TP = True Positive
  • FP = False Positive
  • TP = True Negative
  • FP = False Negative

16.8.2 Accuracy

Accuracy answers a simple question:

How often does the model get the class right?

Accuracy is the proportion of all observations that were classified correctly:

\[ Accuracy = \frac{TP + TN}{TP + TN + FP + FN} \]

We use yardstick’s function for this:

accuracy(predictions, Class, .pred_class)
# A tibble: 1 × 3
  .metric  .estimator .estimate
  <chr>    <chr>          <dbl>
1 accuracy binary         0.802

The accuracy was 0.802. This means that about 80.2% of all participants were classified correctly.

Accuracy is easy to understand, but it has an important limitation:

  • it does not tell us which class the model gets wrong
  • It can also be misleading when the classes are unbalanced.

For example, imagine that 95% of participants were controls. A model that always predicted “control” would have 95% accuracy, despite completely failing to identify anyone with cognitive impairment.

This is why it is useful to look separately at the model’s performance for the different classes.

16.8.3 Specificity

Specificity asks:

Among people who are not “impaired”, how many does the model correctly identify?

Specificity measures how well the model identifies the negative class — here, the control participants.

In other words, specificity is the proportion of actual controls that the model correctly labels as controls.

\[ Sensitivity = \frac{TP}{TP + FN} \]

specificity(predictions, Class, .pred_class)
# A tibble: 1 × 3
  .metric     .estimator .estimate
  <chr>       <chr>          <dbl>
1 specificity binary         0.886

The specificity was 0.886. This means that 88.6% of the participants who were actually controls were correctly identified as controls.

A highly specific model produces few false positives: it rarely labels a control participant as cognitively impaired.

Specificity is therefore particularly useful when false positives are costly or problematic. For example, in a screening context, a false positive might lead to unnecessary further testing or concern.

16.8.4 Sensitivity

Sensitivity asks:

Among people who are “impaired”, how many does the model correctly identify?

Sensitivity measures how well the model identifies the positive class — here, cognitively impaired participants.

\[ Specificity = \frac{TN}{TN + FP} \]

In other words, sensitivity is the proportion of participants who are actually impaired that the model correctly identifies as impaired.

sensitivity(predictions, Class, .pred_class)
# A tibble: 1 × 3
  .metric     .estimator .estimate
  <chr>       <chr>          <dbl>
1 sensitivity binary         0.568

The sensitivity was 0.568. This means that 56.8% of the participants who were actually cognitively impaired were correctly identified by the model.

A highly sensitive model produces few false negatives: it rarely misses a participant who is actually impaired.

This distinction between sensitivity and specificity is important. A model can have high specificity while having relatively low sensitivity, as we see here. Our model is quite good at recognizing controls, but it misses a substantial proportion of participants with cognitive impairment.

16.8.5 Discussion task: Setting a proability threshold

Sensitivity and specificity depend on the chosen probability threshold. We used 0.5 above, but there is nothing inherently special about 0.5.

Changing the threshold changes the balance between false positives and false negatives. A lower threshold makes the model more willing to classify someone as impaired. This will generally increase sensitivity, because fewer impaired participants are missed, but it can also decrease specificity, because more controls may be incorrectly labeled as impaired.

Conversely, a higher threshold makes the model more conservative about calling someone impaired. This can increase specificity but may reduce sensitivity.

In a clinical application, the useful threshold should therefore be chosen based on the consequences of the two types of errors, rather than simply because 0.5 is a convenient number.

This is one reason why reporting accuracy alone is often not enough: two models can have similar accuracy while having very different sensitivity and specificity, and those differences can matter a great deal in practice.

16.8.7 Area under the curve (AUC)

The area under this curve is the AUC. Area under the curve is computed as the integral. Instead of doing this by hand, we can use yardstick again:

roc_auc(ad_validation_logistic, Class, .pred_impaired)
# A tibble: 1 × 3
  .metric .estimator .estimate
  <chr>   <chr>          <dbl>
1 roc_auc binary         0.840

AUC can be interpreted as the probability that the model assigns a higher predicted probability to a randomly chosen “impaired” observation than to a randomly chosen “control” observation.

AUC measures discrimination. It does not tell us whether the predicted probabilities themselves are accurate. For this, we need to assess calibration, which is covered in the next section.

16.9 Calibration

Now, we move away from the world of confusion matrices. Recall that the prediction model initially only had probabilities (that is, before we made a decision threshold for a class).

Calibration refers to the agreement between predicted probabilities and observed outcome frequencies. For example, among patients assigned a predicted risk of cognitive decline of 15%, approximately 15% should experience cognitive decline.

In other words:

Are the probabilities generated from the prediction model actually useful as probabilities in reality?

If the answer is no, then any further decisions based on it’s probabilities (threshold, confusion matrix, ROC, AUC, etc) is basically meaningless 😅

So let’s try to evaluate this!

16.9.1 A: Calibration in the large

Calibration-in-the-large (CITL) assesses whether predicted risks are systematically too high or too low overall. It is commonly estimated using logistic regression with the logit of the predicted risk as an offset, fixing its coefficient at 1. The estimated intercept quantifies the overall calibration error.

To estimate the CITL, we use the following logistic regression model:

\[ logit(P(Y = 1)) = α + offset(logit(\hat{p}_i)) \]

where \(\hat{p}_i\) the predicted risk from the original model and the coefficient of logit(\(\hat{p}_i\)) is fixed at 1. The estimated intercept α is the calibration-in-the-large.

  • citl = 1: no overall calibration-in-the-large error.
  • citl < 1: predicted risks are too high on average.
  • citl > 1: predicted risks are too low on average.

Remember the offset from Chapter 14? The key difference is that an offset in Poisson regression adjusts the expected count for exposure, whereas an offset in logistic regression contributes a known term to the log-odds, with its coefficient fixed at 1.

An offset adds a term with its coefficient fixed at 1, rather than estimated. Our model is:

\[ logit(q_i) = α + o_i \] where \(o_i\) are the logit of the prediction-model’s estimated probabilities,

\[ o_i = logit(\hat{p}_i) \]

The interpretation

The model assumes that the known baseline odds, \(\frac{p_i}{1 - p_i}\), enter with exactly the specified probabilities. The regression estimates the adjustment to those odds from the model-predicted odds.

NoteCalibration is more than the CITL!

A CITL = 0 does not mean the model is perfectly calibrated. It means there is no overall calibration-in-the-large error. The predictions can still be poorly calibrated across the range of predicted risks, which is why calibration slope and calibration plots are useful complementary assessments.

16.9.2 B: The calibration slope

So the CITL measures a systematic bias: the average predicted probability is too large. The calibration slope is a measure of the association between observed and predicted tisk of the outcome event across the whole range of predicted risks. So not a systematic error, but a errors across the prediction range.

To estimate the calibration slope, we use another logistic regression model:

\[ logit(P(Y = 1)) = α + ζlogit(\hat{p}) \]

Here, we are interested in estimating ζ (“zeta”), while the model also estimates a separate intercept α. This model is straight forward to interpret and works similarly to other logistic regression models you have worked with.

  • ζ = 1: ideal calibration slope.
  • ζ < 1: typically indicates overfitting, with predictions that are too extreme.
  • ζ > 1: typically indicates underfitting, with predictions that are not extreme enough.
WarningIntercept from the slope model

One important distinction: the intercept from this model is not the same as the calibration-in-the-large.

16.9.3 Running the models in R

The following code demonstrates how to estimate CITL and the calibration slope in R:

citl_model <- ad_validation_logistic |>
  mutate(
    outcome = Class == "impaired",
    logit_p = log(.pred_impaired / (1 - .pred_impaired))
  ) |>
  glm(outcome ~ 1 + offset(logit_p),
      data = _, family = binomial())

broom::tidy(citl_model, conf.int = TRUE, exponentiate = TRUE)

16.9.4 Visualizing calibration

As always, we recommend visualizing any statistical procedure. We can do this in a plot like Figure 16.5. In a calibration plot, the x-axis shows predicted probabilities and the y-axis shows observed outcome proportions. Both axes range from 0 to 100%. The diagonal ideal line represents perfect calibration: for example, a predicted risk of 15% corresponds to an observed outcome proportion of 15%.

Because the outcome is binary, we cannot directly compare each individual’s predicted probability with an observed proportion: each individual either experiences the outcome or does not. Instead, calibration plots often group individuals into bins/bockets based on their predicted risks. Within each bin, we calculate the mean predicted risk and the observed proportion of individuals who experienced the outcome. These values provide a summary of predicted and observed risk for that group.

For example, consider a validation dataset divided into five bins according to predicted risk:

Bin Mean predicted risk (x-axis) Observed outcome proportion (y-axis) Interpretation
1 (0%—19%) 5% 4% Slight overprediction
2 (20%—39%) 15% 15% Perfect calibration
3 (40%—59%) 30% 35% Underprediction
4 (60%—79%) 50% 45% Overprediction
5 (80%—100%) 80% 75% Overprediction

Each row corresponds to a point in the calibration plot, with mean predicted risk on the x-axis and observed outcome proportion on the y-axis. Points below the diagonal indicate overprediction, while points above the diagonal indicate underprediction. In practice, the number of bins and their boundaries affect the plot, and the observed proportions can be imprecise when bins contain few individuals.

The probably package provides a nice function for plotting the calibration curve:

cal_plot_breaks(
    ad_validation_logistic,
    Class,
    .pred_impaired,
    num_breaks = 5 # number of bins we want
    )

A well-calibrated model follows the diagonal line.

We can also visualize a smooth calibration curve, which assesses calibration across the range of predicted risks without relying on fixed bins:

cal_plot_logistic(ad_validation_logistic, Class, .pred_impaired, smooth = TRUE)

Now, how does the plot look? 👀

Notice how the prediction-model we are validating is generally over-predicting? You can tell from, e.g., bin two in Figure 16.5 — the model (x-axis) give ~30% probability for a bunch of predictions that have an event rate of ~13% probability. So the model is giving predictions far above what it should!

This also corresponds to our CITL being below 1 and our slope being below 1.

So we’ve covered calibration 🎉

Calibration is about the accuracy of the predicted probabilities. But a model can have excellent discrimination and poor calibration — that is, it may correctly rank individuals from lower to higher risk while systematically overestimating or underestimating their absolute risks. To evaluate discrimination, we use the C-statistic.

16.10 Discrimination using the concordance statistic

Discrimination refers to the ability of the model to distinguish a patient with the endpoint (cognitive impairment) from a patient without (control). A better discriminating model has more spread between the predictions than a poorly discriminating model.

Consider the extreme example where a model predicts all subjects to have the same predicted risk as the incidence. This model would have perfect calibration — but it would be useless since it does not discriminate between patients! 😅

A validation plot showing a wide spread between predictions as a histogram, or between deciles of predicted risk, indicates a good discriminating model, see Figure 16.5.

We use the concordance (c) statistic as an outcome for the models ability to discriminate between groups. For a binary endpoint, c is identical to the AUC Section 16.8.7.

In our data, we have a AUC of 0.840 — so the c-statistic (i.e., concordance) is also 0.84.

Intuition of C-statistic

Imagine you play a game with your model. You pick every possible pair of people from your data where one person had the event (1) and the other person did not (0).

You ask your model:

“Which of these two people had a higher predicted probability of the event?

There are three possible outcomes for each pair:

  1. Concordant pair: The model assigns a higher predicted probability to the person who actually had the event (1) than to the person who did not (0).
  2. Discordant pair: The model gets it backward and assigns a higher probability to the person who did not have the event (0).
  3. Tied pair: The model assigns the exact same probability to both people.

The c-statistic is simply the percentage of pairs that are concordant (plus half of the tied pairs) out of all possible pairs.

\[ \text{c-statistic} = \frac{\text{Concordant pairs} + 0.5 × \text{Tied\ pairs}}{\text{Total\ pairs}} \]

16.11 Decision-curve analysis

While calibration and discrimination are important for validating prediction model, neither reflect real clinical usefulness. Clinical usefulness can be boiled down to the ability to make better decisions with a model than without.

If a prediction model aims to guide treatment decisions, a cut-off is required to classify patients as either low risk (no treatment) or high risk (treatment is indicated). The cut-off is a decision threshold.

You will learn about decision-curve analysis in Workshop 3, where you will learn to specify a clinical action and the range of probability thresholds at which that action would be taken.

16.12 Internal and external validation

Everything we’ve done so far has been an internal validation — what do we mean by “internal”?

Recall that we initially made an arbitrary split of the data: all odd-numbered patient IDs were assigned to a test set and the even-numbered IDs to a validation set. Had we used all the data for our model, we could not have performed any independent validation!

16.12.1 Internal validation

Validating internally — using data from the same study or dataset that was used to develop the model — is useful for several reasons.

First, it allows us to estimate how well our model is likely to perform on new patients from the same target population. We can use part of our data to develop the model and hold back another part to evaluate its performance.

However, simply making one arbitrary split into training and validation data has some disadvantages. The estimated performance can depend heavily on which patients happen to end up in each set. With a small dataset, this can lead to substantial uncertainty in our estimate of model performance.

Cross-validation is a more robust way of making internal splits.

In \(k\)-fold cross-validation, we divide the data into \(k\) roughly equal-sized groups, or folds. We then:

  1. Fit the model using \(k - 1\) folds.
  2. Evaluate the model on the remaining fold.
  3. Repeat this process k times, until every fold has been used as the validation data.
  4. Average the results across all folds to obtain an estimate of model performance.

For example, in 5-fold cross-validation (see Figure 16.6), each patient is used for validation once and for model development four times.

Cross-validation therefore makes more efficient use of a limited dataset than a single train/test split. It is particularly useful when the available dataset is relatively small.

To get the k-fold cross-validation AUC, you would have to run the regression model k times, each time splitting the data in a new way (see Figure 16.6). Thereby, you would get k AUC estimates. The AUC you would report would be:

\[ \frac{1}{k}\sum^k_{k=1}\text{AUC}_k \]

It is common to use 5 or 10 folds.

Importantly, cross-validation is still internal validation. The patients used to evaluate the model come from the same underlying study and therefore may share characteristics with the patients used to develop the model.

16.12.2 External validation

Validating externally — using data from other studies, hospitals, populations, or settings — is necessary if we want to know whether a model generalises beyond the data on which it was developed.

A model can perform very well during internal validation but perform much worse when applied to new data. This can happen because the new patients, clinical practices, measurements, or disease prevalence differ from those in the development dataset.

External validation therefore provides a much stronger test of whether a prediction model is likely to be useful in practice.

There are several ways in which we can perform external validation.

  1. Temporal validation:
    Develop the model using data from an earlier time period and evaluate it using patients from a later time period. This tests whether the model continues to work as patients and clinical practice change over time.

  2. Geographical validation:
    Develop the model using data from one geographical location, such as a hospital or country, and evaluate it using data from another location. This tests whether the model generalises to a different population or healthcare setting.

  3. Domain validation:
    Develop the model in one type of healthcare setting and evaluate it in another. For example, a model developed using patients from a specialist hospital could be evaluated in primary care.

  4. Cross-setting validation:
    Develop the model using one study and evaluate it using an entirely independent study. This is often the strongest form of external validation because the validation data were collected independently of the model development process.

The further the external validation data are from the development data, the more demanding the test of generalisability becomes.

16.12.3 When to use internal and external validation?

Internal and external validation can be seen as two levels of evidence:

Internal validation as the initial and inexpensive validation:

  • Statistical estimation of overfitting/underfitting
  • Best guess for future external validation and generalizability
  • Always possible

External validation as the necessary validation check:

  • Does my model still perform well when applied to genuinely new data from > another time, place, setting, or study?

A model should therefore not be considered ready for widespread clinical use simply because it performs well on its development data or under internal validation. External validation is needed to establish whether the model generalises to the population and setting in which we ultimately want to use it.

16.13 Sample size calculation in binary prediction studies

Before investing money and time in a prediction study, it’s often relevant to make inexpensive and sophisticated guesses on how many participants one needs to include before being able to say with confidence whether the model has potential or is useless.

Sample size calculations for prediction models need special care and are slightly different from causal effect studies.

16.13.1 Manual estimation using the c-statistic

Let’s define how we can determine the minimum sample size needed for a new external validation study of a prediction model for a binary outcome.

The calculations can also be used to inform whether the sample size of an existing (i.e., already collected) dataset is adequate for external validation

When externally validating a prediction model, sample size should be large enough to estimate model performance with sufficient precision. Riley et al. (2) propose calculating the required sample size separately for several performance measures and then using the largest required sample size.

In this course, however, you’ll learn to compute only one estimate by hand, but three methods using R code.

For sample-size planning, we need to select:

  • the anticipated C-statistic, \(C\);
  • the anticipated event proportion, \(\phi\); and
  • the desired precision, expressed as \(SE(C)\).

Riley et al. (2) use an approximate formula for the standard error:

\[ 𝑆𝐸(𝐶) ≈ \frac{\sqrt{𝐶(1 − 𝐶) (1 + (𝑁𝜙 − 1)1 − 𝐶2 − 𝐶 + (𝑁(1 − 𝜙) − 1)𝐶1 + 𝐶)}} {𝑁2𝜙(1 − 𝜙)}. \]

This equation is not conveniently rearranged to give \(N\) directly. Instead, we will have to try different values of \(N\) until the resulting \(SE(C)\) is sufficiently small.

For example, suppose:

\[ 𝐶 = 0.70, \\ 𝜙 = 0.10. \]

If we want the C-statistic to have an approximate 95% confidence interval of \(\pm0.05\), we need approximately

\[ 𝑆𝐸(𝐶) = \frac{0.05}{1.96} ≈ 0.0255. \]

We then increase \(N\) until the formula gives \(SE(C) \approx 0.0255\).

The resulting \(N\) is the required validation sample size for the C-statistic criterion.

In this case, it is:

\[ SE(C) \approx \sqrt{\frac{0.70(1 - 0.70)}{1413^2(0.10)(1 - 0.10)} \Bigg[1 + (1413 \times 0.10 - 1)\frac{1 - 0.70}{2 - 0.70} + (1413 \times (1 - 0.10) - 1)\frac{0.70}{1 + 0.70}\Bigg]} \approx 0.0255 \]

so \(N = 1413\)

# Our selected values
p  <- 0.70
n  <- 1000:1500
pi <- 0.10

# Compute the first fraction
broek <- (p * (1 - p)) / (n^2 * pi * (1 - pi))

# Break up the large formula insude the square brackets [ ] at every plus sign
led_1 <- 1
led_2 <- (n * pi - 1) * ((1 - p) / (2 - p))
led_3 <- (n * (1 - pi) - 1) * (p / (1 + p))

# Take the sqrt of it all
SE_C <- sqrt(broek * (led_1 + led_2 + led_3))

# Visualize values
ggplot(data.frame(n,SE_C),aes(n,SE_C)) +
    geom_line() +
    geom_hline(yintercept=0.0255) +
    geom_text(aes(label = "x"), x = 1413, y = 0.0255, size = 5, color = "red")

The interpretation is:

How many patients do I need to estimate the model’s ability to discriminate between patients with and without the outcome with the desired precision?

Because the C-statistic depends on comparisons between events and non-events, both the number of events and the number of non-events contribute information.

Be aware that many more sample size calculation methods exists! Best practice is to use several estimators and take the most conservative number (i.e., the largest value). But some of the other estimators are quite complicated and out of the scope of this course. Luckily for us, R provides easy access to the more complicated estimators.

16.13.3 Summary

A useful way to remember prediction-model evaluation is the ABCD framework:

  • A — Calibration-in-the-large: are predictions systematically too high or too low?
  • B — Calibration slope: are predictions too extreme or not extreme enough?
  • C — C-statistic: how well does the model discriminate between outcomes?
  • D — Decision curve: does using the model improve clinical decisions?

This framework separates statistical performance from clinical usefulness.

A simple evaluation therefore looks like this:

Question Measure
Does the model classify correctly at this threshold? Accuracy
Does it avoid false positives? Specificity
Does it avoid false negatives? Sensitivity
Can it distinguish the two outcomes? ROC / AUC
Are the probabilities accurate? Calibration
Does it improve clinical decisions? Decision curve
What is the effect of a predictor? Effect estimate

The key idea is that no single metric evaluates a prediction model completely.

A useful model should discriminate well, produce sensible probabilities, and — most importantly — lead to better decisions.

required_N <- function(C, phi, desired_SE) {

  # Check inputs
  if (C <= 0.5 || C >= 1) {
    stop("C must be greater than 0.5 and less than 1.")
  }

  if (phi <= 0 || phi >= 1) {
    stop("phi must be between 0 and 1.")
  }

  if (desired_SE <= 0) {
    stop("desired_SE must be positive.")
  }

  # Standard error as a function of N
  se_fun <- function(N) {
    sqrt(
      C * (1 - C) /
        (N^2 * phi * (1 - phi)) *
        (
          1 +
            (N * phi - 1) * (1 - C) / (2 - C) +
            (N * (1 - phi) - 1) * C / (1 + C)
        )
    )
  }

  # Find N such that SE(C) equals desired_SE
  result <- uniroot(
    function(N) se_fun(N) - desired_SE,
    interval = c(2, 1e9)
  )$root

  # Round up to the next whole participant
  N <- ceiling(result)

  # Return sample size and expected event counts
  list(
    N = N,
    expected_events = N * phi,
    expected_non_events = N * (1 - phi),
    achieved_SE = se_fun(N)
  )
}
